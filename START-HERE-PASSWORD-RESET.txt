FORGOT PASSWORD — EMAIL RECOVERY

INSTALL
1. Back up current code/data, extract this ZIP.
2. Replace Code.gs with APPS-SCRIPT-CODE.gs; save.
3. Run setup to add PasswordResets. Existing data is preserved.
4. Email permission was already granted for signup verification. If prompted, approve it again; authorizeEmailVerification checks the permission without sending email.
5. Deploy > Manage deployments > pencil > New version > Deploy. Keep the same URL, Execute as Me setting, and all Script Properties (including EMAIL_VERIFICATION_SECRET).
6. Close old tabs and open this index.html.

TEST
Use an existing account you control. Log in in one tab, then in another tab open Login > Forgot password? Enter its registered email, check Inbox/Spam, enter reset code and new password twice. Then log in with the new password. The old password and earlier sessions should no longer work; an already open tab loses access on its next protected request, not instant remote UI erasure. Approval/disabled status is not changed. Admin recovery uses the registered admin email, including legacy non-school addresses.

SAFETY
Six-digit code expires in ten minutes. Five wrong attempts lock a challenge. Resend after sixty seconds, maximum three sends per challenge and five per email per hour; resending invalidates the previous code without clearing failed attempts. Only a hash is stored for code/password; plaintext passwords are not stored in reset data or operation logs. Completion returns no login token: user must log in again. Unused reset records cannot activate accounts or verify new signups. Deleting/recreating an account invalidates its earlier reset challenge.

The request message is intentionally generic for registered and unregistered emails. If no code arrives, check the address, spam, school filters and administrator email quota/permissions. A pending request reuses its challenge: check the earlier message or Resend code. If locked, wait for current expiry and start again. Closing a tab may lose the saved challenge pointer; requesting again while a challenge is active recovers that challenge.

Emails are sent by Apps Script under the deployment owner account, not WhatsApp/Twilio/Gemini. MailApp acceptance is not guaranteed inbox delivery. No live email was sent during assistant's local simulated tests. Signups still require school email verification; all prior features remain. Automatic WhatsApp sending stays paused.

LIMITATIONS
Still a small trusted beta, not production-grade managed authentication. Password hashing/session storage limitations from the existing app remain. Expired reset metadata remains in PasswordResets until owner removes expired rows. Keep underlying data private. Requests already authorized before reset may finish; future protected requests require a new session.
